## 实质改动

1. **ADS8688 原生两通道 1000 Hz**：保留正确的独立 CS 转换帧，在采集期间关闭 SPI 控制器的自动休眠；专用采集进程使用 FIFO 优先级 10 和 1 ns timer slack 请求。实际时间间隔仍有 Linux 调度抖动，目标 1 ms 不等于硬实时保证。
2. **IMU 每条 I²C 一个独立进程**：硬件输出配置仍为已确认的 200 Hz；采集时保持控制器唤醒，避免界面 GIL、绘图与保存阻塞硬件读取。四只分别保留在线/断线、独立时间戳、重复寄存器诊断和原来的参考姿态功能。两段寄存器读数不保证是同一内部解算周期；重复读到相同寄存器块不等于产生了新硬件样本。
3. **电机两条串口独立线程**：每条端口有自己的锁和命令/反馈对象，不再让两个串口依次等待。校验失败不保存旧反馈为新数据；Stop 的零输出命令使用同一端口锁。端口文件锁阻止本界面重复占用。新增 `host_round_trip_ms`，表示主机请求到有效回复的耗时，不能当成单向传输延迟直接扣除。实机验证仅使用零输出监测；有负载的控制行为尚未实测。
4. **20 ms 有界批量交接，300 ms 周期写盘**：采集与落盘节奏分开。60 ms × 5 的记录结构暂时保留，因为实测瓶颈在采集调度和总线，不在这个分包长度。数据写入专用进程，预留本机发送订阅接口。
5. **消除每 30 秒集中裁剪显示缓存**：新模式使用 `maxlen=8000` 的固定长度环形缓存，随新样本逐个淘汰旧样本。旧集中清理曾造成电机约 200 ms 的读取空档；不再为减少瞬时缓存而周期性阻塞采集。写盘队列、等待窗口和图片队列继续保留硬上限。

6. **隐藏页面停止重绘**：后台数据更新保持，切回页面显示最新数据；IMU九类曲线复用每路时间切片，减少重复遍历。

## 满负载写盘修复

延长合成测试时曾触发队列满，正确标记记录不完整。最终把解码、数值接受与周期写盘合为子进程中的一个消费者，删除重复的数值队列和帧字典复制，减少 Python 执行锁争用；图片交给独立 PNG 编码进程处理，仍保持16位无损深度值，压缩等级从1调整为3。数值文件使用256KiB固定写缓冲（全部18个数值文件最多约4.5MiB），减少小块系统写入，仍按300ms周期flush；重采样只遍历当前周期需要的时间范围。

父记录队列仍限2048项/64MiB，IPC单包最多64MiB；子进程只持有当前数值包，通过socket对上游自然减速。图像队列仍限64帧，编码进程只处理一帧，数据等待窗口仍默认3秒。没有增加队列容量。父队列持续过载仍明确报错，错误同时写入最终质量文件。兼容的线程写盘模式仍保留有界队列；其 `queue_backpressure_waits` 统计内部等待，默认进程模式则查看 `parent_max_queue_depth` / `parent_max_queued_bytes`。验收必须共同检查完整帧数、迟到、乱序、溢出及停止排空。

此外，每个300ms周期把刚写入的文件范围提交给 Linux 后台回写，PNG完成后也及时提交。这样控制的不仅是 Python 队列，也减少内核待写页积攒后集中回写造成的停顿。只作用于本次记录文件，不修改全局VM参数；`HIPEXO_ASYNC_WRITEBACK=0` 可用于对照测试。该调用用于平滑I/O，**不等同于fsync，也不是断电持久化保证**；依据见 [Linux sync_file_range 手册](https://man7.org/linux/man-pages/man2/arm_sync_file_range.2.html)。

## 调度与恢复

界面仍以普通用户运行。只有 `sudo -n chrt` 和指定控制器 `power/control` 写入尝试提权，不弹密码框，不修改系统全局频率、功耗模式、内核或设备树。权限不足时继续普通调度，并在状态日志显示失败，不能据此假定已达到 1000 Hz。

控制器电源策略由父进程持有排他租约；结束采集或强制结束采集子进程后恢复原值。若整个父进程被 SIGKILL 或电脑断电，清理代码无法执行；下一次取得相同租约时会依据保留状态恢复。线程/进程退出后其调度策略自然消失。调试时可用 `HIPEXO_DISABLE_TUNING=1` 关闭全部提权调优；这可能降低频率。

IMU 在正常启停中不反复写 Flash。`HIPEXO_IMU_IN_PROCESS=1` 仅作为旧线程实现的调试回退；正式默认使用独立采集进程。

## 硬件限制与未通过的试验

- 当前 I²C-7 为 400 kHz，I²C-1 为 100 kHz。后者两只合计总线时间接近 5 ms，独立总线短测最高约每只 195 次读取/秒。单纯提高 Python 目标频率无法增加这个总线带宽。若要再提高，需要核对模块/上拉/接线后提高控制器总线速率；本版未重启或修改设备树。
- 对电机尝试过 1000 次/秒连续零命令发送。它能提高反馈吞吐，但出现校验错误和缺失；该实验路径没有并入正式控制/采集。当前正式路径等待每次有效反馈，低于 1000 Hz 的部分在处理网格上按实际时间重采样。
- 本轮实机联测包含四 IMU、两路力传感器及两电机零输出反馈。相机未检测到；Windows EMG、LiDAR 未在本轮实机验收。合成负载测试不替代这些设备的实测。

## 文件和兼容性

`pipeline_schema.json` 标识 `hipexo-cycle/2`，`acquisition_config.json` 标识 `hipexo-acquisition/2`。列顺序以每次记录的 schema 为准，不硬编码位置。V2 增加两路电机往返耗时列，其余质量码和时间约定保持。真实读取率在 `pipeline_quality.json` 的每路 `accepted_rate_hz`；它仍不是设备内部转换/解算频率的证明。

GitHub 仅发布代码、说明、明确标为 SIMULATED 的样例；实测波形、个人记录、EMG 凭证和本机 SDK 二进制只留本机。备份位置和版本验收结果见本机部署记录及 [验收报告](docs/VALIDATION.md)。
